# ADR 0015: Generate sitemap.xml and robots.txt in Next.js

*   **Status**: Accepted
*   **Date**: 2026-07-05
*   **Deciders**: Patryk O
*   **Context Docs**: [Vercel Frontend Deployment](0009-vercel-frontend-deployment.md), [Headless Content Delivery](0003-headless-content-delivery.md)

## Context

Sulu ships built-in sitemap tooling (`Sulu\Bundle\WebsiteBundle\Sitemap\*`,
`SitemapController`, `sulu:website:dump-sitemap`), exposing a `/sitemap.xml`
(and paginated per-provider sitemaps) on the webspace's own host. It's
tempting to reach for this instead of building anything new, per this
project's general preference for Sulu's built-in capabilities over custom
solutions.

It doesn't fit here:

*   Per [ADR-0009](0009-vercel-frontend-deployment.md), Next.js on Vercel is
    the only public frontend; the Sulu backend's `api_domain` nginx vhost
    (`ansible/roles/nginx/templates/app.conf.j2`) deliberately proxies only
    `*.json`, `/api/*`, `/media/*`, and a narrow `/admin/api/preview/`
    carve-out — everything else, including `/sitemap.xml`, 404s. The vhost's
    own comment states the intent directly: "HTML rendering is blocked —
    Next.js on Vercel is the only frontend."
*   Even with a nginx carve-out added, Sulu's sitemap would be served from
    the API domain (`api.yourdomain.com`), not the canonical public domain
    end users and crawlers see (`yourdomain.com`) — the wrong host for a
    sitemap to be discovered at.
*   Every public route in this app is already a Sulu page/article resolved
    through the single Next.js catch-all (`app/[[...slug]]/page.tsx`) via
    the existing headless delivery client (`lib/sulu.ts`). Reusing that same
    client to enumerate content for a sitemap doesn't introduce a new API —
    it's the existing one, called one more way.

## Decision

Generate `sitemap.xml` and `robots.txt` in Next.js, using the Next.js App
Router conventions (`app/sitemap.ts`, `app/robots.ts`) backed entirely by
`lib/sulu.ts`'s existing functions:

*   **Sitemap** (`app/sitemap.ts`): static entries for `/`, `/authors`, and
    `/learning-paths`, plus every author (from the `/authors` listing
    content's `authors` array), every learning path (from the
    `/learning-paths` listing content's `paths` array), and every article
    (paginating `getArticles` to completion). No new backend endpoint.
*   **Robots** (`app/robots.ts`): allow all, disallow `/search` (query-param
    driven, thin/duplicate content), and reference the generated sitemap.
*   **`metadataBase`**: set on the root layout from a new `SITE_URL` server
    env var (not `NEXT_PUBLIC_SITE_URL` — nothing here runs client-side, and
    every other backend-URL-shaped env var in this app, `SULU_BASE_URL`,
    `PREVIEW_SECRET`, is server-only by the same reasoning), so
    canonical/OG URLs resolve correctly instead of defaulting to
    `localhost`.

Per-article `noIndex`/`hideInSitemap` flags (`extension.seo`) are **not**
consulted when building the sitemap — `getArticles`'s search-hit shape
doesn't carry the SEO extension, and fetching each article individually to
check one boolean would turn an O(1) paginated listing into O(n) full-content
fetches for a showcase project with no traffic-scale concerns. The existing
per-page `robots` meta tag (already wired in `generateMetadata`, see
`app/[[...slug]]/page.tsx`) is what actually keeps a noindexed page out of
search results; a stray sitemap entry for it is a minor, accepted
imperfection, not a functional gap.

## Consequences

### Positive

*   Zero new backend surface — no new Sulu controller, no new nginx
    carve-out, no new attack surface on `api_domain`.
*   Sitemap and canonical URLs are naturally correct for the domain crawlers
    actually see, since they're generated by the same app serving that
    domain.
*   Reuses `lib/sulu.ts` exactly as-is; no divergent second content client.

### Negative / Risks

*   A page with `extension.seo.noIndex: true` can still appear in the
    sitemap (see above) — acceptable trade-off, not fixed here.
*   `hideInSitemap` (already fetched into `SuluSeo` for the per-page
    `robots` meta) has no effect on sitemap inclusion. If per-item sitemap
    exclusion becomes a real requirement, revisit by either denormalizing a
    `noIndex`/`hideInSitemap` flag into the article search-hit shape
    (`SuluSearchHit`) so `getArticles` can filter without extra fetches, or
    accepting the O(n) cost if content volume stays small.
*   Sulu's own sitemap/`dump-sitemap` machinery remains installed but
    unused and unreachable — dead weight in the vendor tree, not a live
    footgun, since nothing routes to it.

## Alternatives Considered

1.  **Expose Sulu's built-in `/sitemap.xml`** via a new `api_domain` nginx
    carve-out. Rejected: wrong domain (API host, not the canonical public
    host), and widens the API vhost's deliberately narrow allowlist for a
    feature the frontend can already produce itself from data it already
    fetches.
2.  **New Sulu-side JSON endpoint** wrapping `SitemapProviderPool` for
    Next.js to consume. Rejected: would add a custom backend endpoint for
    something achievable by paginating the existing `/api/articles` listing
    plus the two listing pages' own content — no justified need for new
    backend surface per this project's stated preference for built-in
    capabilities and avoiding custom APIs unless required.
